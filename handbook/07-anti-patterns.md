# Anti-patterns

A system fails in predictable ways. These are the common ones.

| Anti-pattern | Why it hurts | Fix |
| --- | --- | --- |
| Process theater | People follow the ritual without the outcome | Tie every practice to an artifact or decision |
| Tool-first adoption | The tool becomes the system | Start with the problem, then choose the tool |
| Stale board | The view stops matching reality | Update status when it changes; review weekly |
| Too many statuses | The board becomes hard to read | Keep five to seven |
| Everything is critical | Priority stops meaning anything | Reserve critical for real commitments |
| No decision log | The same debate returns | Record decisions and reasoning |
| Hero culture | One person becomes the bottleneck | Distribute ownership and document context |
| Over-planning | The plan becomes the work | Plan at the level of the next decision |
| No review | The system never learns | Run a weekly review and a retrospective |
| Metrics as a scoreboard | People optimize the number, not the outcome | Use metrics to inform decisions |
| Copying a big company | The system does not fit the team | Adopt one practice at a time |
| Hidden work | Coordination happens in private messages | Put commitments in the shared view |
| No definition of done | Work lingers at 90 percent | Write done criteria before starting |
| Nested Git repos by accident | Confusing history and tooling | Use a container folder and one repo per source tree |
| Versioning everything | Noise and accidental commits | Version what needs history; leave the rest alone |

## The test

For each practice, ask:

- What artifact does it produce?
- What decision does it improve?
- What would break if we stopped?

If the answer is “nothing,” stop.

## Try it

Pick one anti-pattern you have seen.

Write:

- The symptom.
- The cost.
- The smallest change that would reduce it.
