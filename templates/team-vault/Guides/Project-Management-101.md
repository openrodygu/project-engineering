# Project Management 101

An optional reference for planning techniques. The shared vault is a lightweight team-visibility layer, not a formal project-management process. Use what helps and skip what does not.

Read [[_README|the team workflow]] first.

## Where this fits

- The **shared vault** (dotpm) is for team-level planning, commitments, dependencies, and visible progress.
- Your **personal vault** (TaskNotes) is for individual execution, daily planning, and private notes.
- The two systems are not synced. See [[TaskNotes-Guide]] for the personal side and [[dotpm-Guide]] for the shared side.

Software tutorials: [[Obsidian-Basics]], [[dotpm-Guide]], [[TaskNotes-Guide]].

---

## The mental model

Project management is a loop, not a document:

1. **Define** the outcome and what done means.
2. **Break** the outcome into small pieces of work.
3. **Prioritize** the pieces.
4. **Estimate** and **sequence** them.
5. **Execute** and track reality.
6. **Review**, adjust, and close.

dotpm supports every step, but the thinking is yours. A tool cannot decide what matters.

---

## 1. Define the outcome

Start with a lightweight project brief. Keep it to one screen.

A good brief answers:

- **Goal** — what changes if this project succeeds?
- **Definition of done** — what must be true for us to call it finished?
- **Scope** — what is included?
- **Non-goals** — what are we explicitly not doing?
- **Stakeholders** — who decides, who contributes, who is affected?
- **Constraints** — budget, deadline, people, technology, compliance.
- **Risks** — what is most likely to go wrong?

In dotpm:

- Create one project per outcome.
- Put the goal and definition of done in the project's **description** property, not in the note body. The body is regenerated by the plugin.
- Add the team as **members**.
- Add stakeholders as members too, if you want to filter by them later.

> [!tip] One project per outcome
> "Example Project" is a project. "Automation" is a theme. If the name has no finish line, it is probably a tag or a parent project.

### Project brief template

```markdown
**Goal:** ...

**Definition of done:**
- ...
- ...

**In scope:**
- ...

**Out of scope:**
- ...

**Stakeholders:**
- Decision maker: ...
- Contributors: ...
- Affected: ...

**Constraints:**
- Deadline: ...
- Budget: ...
- People: ...

**Top risks:**
- ...
```

## 2. Break the work down

This is a **work breakdown structure** (WBS). You are dividing the outcome until each piece is small enough to estimate and finish.

Rules that work:

- **The 8–80 rule.** A task should take more than 8 hours and less than 80 hours. Below 8, it is a checklist item. Above 80, it is a project or a parent task.
- **Size for feedback.** Prefer tasks that finish in one to three days. Long tasks hide problems.
- **Deliverable, not activity.** "Draft vendor comparison" is a deliverable. "Work on vendors" is not.
- **Mutually exclusive children.** Two subtasks should not contain the same work.
- **Stop at a useful depth.** Three levels is usually enough. If you need six, the top level is probably a project.

In dotpm:

- Create top-level tasks for the major deliverables.
- Use **Subtasks** for the breakdown. Nesting can go as deep as needed.
- Parent progress rolls up automatically from children.
- If a branch is really its own outcome, make it a **sub-project** instead.

### Breakdown example

```text
Define Scope                  task
├── Research Options          subtask
├── Build Prototype           subtask
└── Write Summary             subtask
```

The parent is the outcome. The children are the work. Nobody has to guess what "Define Scope" means.

## 3. Prioritize

Priority is about consequence and order, not effort. Two simple methods:

### MoSCoW

- **Must** — the outcome fails without it.
- **Should** — important, but there is a workaround.
- **Could** — nice to have.
- **Won't** — explicitly out of scope this cycle.

### Value vs. effort

Plot each task:

| | Low effort | High effort |
| --- | --- | --- |
| **High value** | Do first | Plan carefully |
| **Low value** | Do if cheap | Drop or defer |

### Eisenhower matrix

- Urgent and important — do now.
- Important, not urgent — schedule it.
- Urgent, not important — delegate or batch.
- Neither — delete or archive.

### Map to dotpm priorities

| PM idea | dotpm priority |
| --- | --- |
| Must, urgent, blocks a commitment | **Critical** |
| Must or Should this cycle | **High** |
| Normal planned work | **Medium** |
| Could, or safe to slip | **Low** |

Two disciplines matter more than the method:

- **Limit work in progress.** One person should not have five tasks In Progress. Finish before starting.
- **Protect the critical few.** If everything is Critical, the scale has stopped working.

In dotpm:

- Set **Priority** on every committed task.
- Filter to Critical and High for the weekly plan.
- Use **Blocked** for work waiting on someone, not Low priority.

## 4. Estimate

An estimate is a range, not a promise. The goal is to expose uncertainty early.

### Three-point estimating

For each task, estimate:

- **Optimistic (O)** — everything goes right.
- **Most likely (M)** — normal friction.
- **Pessimistic (P)** — the plausible bad case.

Expected effort ≈ `(O + 4M + P) / 6`.

### Practical rules

- Estimate in hours or half-days, not "days" with no definition.
- Add a **buffer** at the project level, not hidden inside every task. Ten to twenty percent is common.
- Break down anything you cannot estimate. Uncertainty is a signal, not a failure.
- Compare estimates to actuals after the fact. That is how the next estimate gets better.

In dotpm:

- Set **timeEstimate** on a task in the **Time tracking** panel.
- Log actual time with **+ log time**.
- The project overview shows logged vs. estimated.
- If a task blows past its estimate, split it into subtasks with their own estimates.

> [!warning] Big estimates are usually wrong
> "80 hours" on one task hides what is actually three different problems. Break it down until each estimate feels boring.

## 5. Sequence and schedule

Order matters. Some work can happen in parallel; some cannot.

### Dependencies

Use a dependency when one task cannot start until another finishes.

- **Finish-to-start** is the normal case and the one dotpm models.
- A dependency is not a subtask. "Write Summary" is part of "Define Scope" (subtask) and depends on "Build Prototype" (dependency).
- Keep dependency chains short. Long chains create fragile plans.

### Milestones

A milestone is a zero-duration marker for a meaningful checkpoint: "Vendor selected", "Prototype approved", "Handover complete".

- Use milestones for decisions and external commitments.
- Do not use them as tasks. If it takes work, it is a task.
- In dotpm, set a task's **Type** to **milestone**. It renders as a diamond on the Gantt.

### Critical path

The **critical path** is the longest chain of dependent work. Any delay on it delays the whole project. Work not on the critical path has slack.

- Identify the critical path before committing to a date.
- Protect it. Move resources there first.
- Re-check it when dates change.

### Buffers

Put buffer at the end of the project or before a major milestone, not inside every task. A visible buffer is honest. Hidden padding is not.

In dotpm:

- Set **start** and **due** on tasks you are scheduling.
- Add **Depends on** links. The Gantt draws arrows.
- Use the Gantt to drag and resize. Auto-schedule will push dependents forward.
- Remember: auto-schedule only moves dates forward, skips archived and complete tasks, and never moves a task backward unless **Pull dependents forward** is enabled.

> [!tip] Do not over-link
> A dependency means a real constraint. If two tasks can happen in any order, do not link them. Dependency spaghetti makes every date change ripple.

## 6. Execute and track

### The status workflow

| Status | When to use it |
| --- | --- |
| **To Do** | Ready, not started |
| **In Progress** | Someone is actively working |
| **Blocked** | Waiting on a decision, dependency, or external party |
| **In Review** | Work complete, waiting for check or sign-off |
| **Done** | Accepted |
| **Cancelled** | Deliberately stopped |

Rules:

- One task per person In Progress at a time, unless the work genuinely interleaves.
- Update status the day it changes.
- **Blocked** is not a parking lot. Write the blocker and the person who can unblock it.
- **In Review** needs a named reviewer, or it will sit forever.

### Progress

- Update **progress** on leaf tasks.
- Parent progress rolls up from children. Do not fake a parent percentage.
- Prefer moving a task to Done over setting it to 90 percent for a week.

### Blockers

A blocker is a risk that has already happened. Record it:

```markdown
**Blocker:** Waiting on an external vendor for the pricing sheet.
**Owner:** <name>
**Needed by:** YYYY-MM-DD
**Impact:** The summary cannot be finalized; it slips by two days.
**Next action:** Follow up on <date>.
```

Put this in the task description, set status to **Blocked**, and raise it in the next standup. Do not leave it in a chat thread.

### Daily check-in

A short daily pass is enough:

1. What did I finish?
2. What am I doing next?
3. What is blocking me?
4. Does any due date need to change?

In dotpm: open your saved **My work** view, update statuses, and fix dates. Two minutes.

## 7. Review and close

### Weekly review

Run this once a week. It is the highest-value habit in project management.

1. Open the project **overview**. Check progress, overdue count, and next milestone.
2. Open the table and filter **Overdue**. Reschedule, finish, or cancel each item.
3. Filter **Blocked**. Confirm each blocker has an owner and a next action.
4. Filter **Due this week**. Confirm the plan is realistic.
5. Check **In Review**. Nudge reviewers.
6. Look at the **critical path** on the Gantt. Is anything slipping?
7. Update the project description if scope or done criteria changed.
8. Archive finished work.

### Definition of done

Use a shared checklist so "Done" means the same thing to everyone:

```markdown
- [ ] Deliverable meets the acceptance criteria in the description
- [ ] Reviewed by someone other than the author
- [ ] Documentation or handover notes updated
- [ ] Stakeholder informed or signed off
- [ ] No open blockers
```

### Retrospective

At the end of a phase or project, spend 30 minutes on:

- **What went well?** Keep doing it.
- **What did not?** Name the cause, not the person.
- **What will we change?** Pick one or two concrete changes.
- **What did we learn?** Link notes and decisions.

Record the retro in the project description or a linked note, then archive the project.

### Closing a project

1. Confirm the definition of done is met.
2. Move remaining open tasks to **Cancelled** or a follow-up project.
3. Archive completed tasks.
4. Archive the project if it is truly finished.
5. Write a short close-out note: outcome, dates, actual effort, lessons.

## Technique-to-dotpm cheat sheet

| Technique | Do this in dotpm |
| --- | --- |
| Project brief | Project **description** property |
| Work breakdown structure | Tasks + **Subtasks** |
| Workstream split | **Sub-project** |
| MoSCoW / Eisenhower | **Priority** field (Critical–Low) |
| WIP limit | Filter by assignee, count **In Progress** |
| Three-point estimate | **timeEstimate**; log actuals in **timeLogs** |
| Buffer | A task or milestone reserved at the end of a phase |
| Dependency | **Depends on** in the task editor |
| Critical path | Gantt view with dependency arrows |
| Milestone | Task **Type = milestone** |
| Status workflow | **Status** field; board columns |
| Blocker log | **Blocked** status + description |
| Progress rollup | Parent progress from subtasks |
| Weekly review | Project **overview** + saved views |
| Definition of done | Checklist in the task or project description |
| Retrospective | Linked note or project description |
| Archive | Move to `_tasks/Archive/` (use the UI) |

### Shared vs. personal

| Need | Use |
| --- | --- |
| A team commitment, status, dependency, or milestone | dotpm in the shared vault |
| A personal daily plan, focus block, or reminder | TaskNotes in your personal vault |
| A planning technique or template | This guide |

The shared vault is authoritative for what the team has agreed to. The personal vault is authoritative for how you execute your own work. Do not keep two active copies of the same commitment.

## Common anti-patterns

| Anti-pattern | Why it hurts | Fix |
| --- | --- | --- |
| Mega-project with hundreds of tasks | Nobody can see the plan | Split into sub-projects |
| Checkbox-only tasks | No owner, no date, no accountability | Add assignee, due date, and a verb title |
| Everything is Critical | Priority stops meaning anything | Reserve Critical for commitments |
| Five tasks In Progress per person | Nothing finishes | Enforce a WIP limit |
| Blocked with no explanation | The blocker is invisible | Write the blocker and next action |
| Fake parent progress | Reports lie | Update leaf tasks and let rollup work |
| Dependency spaghetti | Every change ripples | Link only real constraints |
| Due dates with no buffer | The plan is fragile | Add a visible phase buffer |
| Never archiving | The board becomes noise | Archive at the end of each cycle |
| Editing generated task body | Changes get overwritten | Put prose in the description above generated lines |
