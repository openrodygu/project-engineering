# Solo PM

One person, one project, a light setup. The point is to keep the plan and the work in the same place without building a process for a team that does not exist.

## The setup

- A [project brief](../resources/templates/project-brief.md) in a notes folder.
- A personal vault with [personal vault](../templates/personal-vault/_README.md) for daily execution.
- A Git repository in `source/` if the project produces code or files.
- A short weekly review with yourself.

You can skip the shared team vault until someone else needs visibility. If you do keep one, use it only for the few things you want to see at a glance.

## Kickoff

Fill in the brief in 20 minutes.

- Outcome: what will be true when this is done?
- Scope: what is in and what is out?
- Definition of done: how will you know?
- First milestone: the first useful result.
- Risks: what could stop you?

Then create the first milestone's tasks in TaskNotes. Keep the list short.

```text
Personal vault
└── TaskNotes
    ├── Write project brief
    ├── Research two options
    ├── Build first version
    └── Review with stakeholder
```

## A normal week

1. **Monday:** pick the few tasks that move the milestone. Put them on the calendar.
2. **Daily:** work from today's list. Update status when it changes.
3. **Friday:** run the [weekly review](../resources/checklists/weekly-review.md) with yourself. Close what is done, reschedule what slipped, and drop what no longer matters.
4. **When a real choice appears:** write a short [decision record](../resources/templates/decision-record.md). Future you will want the reasoning.

## What to skip

- A formal status update for an audience of one.
- A dependency graph unless the order truly matters.
- Sprint ceremonies.
- A shared board that only you open.
- Metrics that do not change a decision.

## What to keep

- The brief. It keeps scope from drifting.
- The weekly review. It catches a stale list.
- The decision record. It stops you from re-deciding the same thing.
- Git history for anything that changes over time.

## When to add structure

Add a shared view when:

- Someone else needs to see status.
- A second person starts doing work.
- You are waiting on another team.
- The project has more than one workstream.

Then move to the [small team](small-team.md) pattern.
