# Sharing and publishing

Sharing a vault means giving other people access to the folder or to a published view. Both need a clear rule about what is visible.

## Share the folder

The team vault is usually shared through a drive or folder that the team can open. Decide three things before you invite anyone:

1. **Who can read.**
2. **Who can edit.**
3. **Where the authoritative copy lives.**

A shared folder with one authoritative copy avoids the "which version is current?" problem. If someone needs a snapshot, give them a copy, not a second live copy.

## Publish a view

Obsidian Publish and static exports can make notes readable outside Obsidian. Publish is useful for:

- Onboarding guides.
- A project status page.
- A public decision record.

Publish the smallest set of notes that answers the reader's question. Do not publish the whole vault and rely on people not clicking around.

## Protect private notes

Before publishing or sharing, check for:

- Personal notes and daily plans.
- Names, customer details, or internal links.
- Tokens, passwords, and local API settings.
- Comments that were written for the team, not for an outside reader.

The two-vault model helps here. Personal work stays in the personal vault, and the shared vault holds material the team already expects others to see.

## Sharing with non-engineers

Give readers a starting page, not a folder tree. One page with context, current status, and a link to the next useful note beats a perfect structure nobody can navigate.

When you share a status view, say when it was last updated. A stale dashboard is worse than no dashboard.

## Try it

Write a one-paragraph sharing rule for your project:

> This vault lives at ______. ______ can read it, ______ can edit it, and the authoritative copy is ______. We never put ______ in it.

Keep the rule in the team vault's `_README.md` or in the project note. Then check one published or shared page against it.
