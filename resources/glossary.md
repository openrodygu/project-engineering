# Glossary

The terms used across this repo. Definitions are short and practical.

## A–C

**Adoption** — Using a practice long enough to decide whether it helps. One practice at a time is enough.

**ADR** — Architecture Decision Record. A short note that captures a significant decision, its context, and its trade-offs. See [Decision record](templates/decision-record.md).

**Artifact** — A concrete output such as a brief, task board, commit, decision record, or retrospective note. If a practice produces no artifact, it is probably a habit.

**Backlog** — Work that is known but not yet committed. A backlog is a list, not a plan.

**Blocker** — Something outside the work that stops it. A blocker needs an owner and a stated waiting condition.

**Cadence** — The rhythm of updates and reviews. A common one is daily updates, a weekly review, and a retrospective at project close.

**Critical path** — The longest chain of dependent work that sets the earliest possible finish date. Delays on this path delay the project.

**Cycle time** — How long a task takes from when work starts to when it is done. It measures execution.

## D–L

**Decision record** — A written account of a choice and the reasoning behind it. Keeps the same debate from returning. See [Decision record](templates/decision-record.md).

**Definition of done** — The conditions that must be true before work is accepted. Write it before starting, not after.

**Definition of ready** — The conditions that make a task ready to start: clear outcome, owner, and enough context. Optional, but useful when work stalls at pickup.

**Dependency** — Work that must happen before or alongside other work. Use it for real order, not for every loose connection.

**dotpm** — The Obsidian plugin used in the team vault for shared projects, tasks, status, and dependencies.

**Lead time** — How long work takes from request to done. It includes waiting, so it is usually longer than cycle time.

## M–R

**Milestone** — A checkpoint with a date and evidence. It marks a result, not a meeting.

**Outcome** — The result the work is meant to produce. An outcome is something that becomes true, not a list of activities.

**Project** — A bounded effort with an outcome and a finish line. "Automation" is a theme; "Reduce close time by 20 percent by June" is a project.

**Project brief** — A one-page summary of outcome, scope, stakeholders, deliverables, done criteria, milestones, and risks. See [Project brief](templates/project-brief.md).

**Project engineering system** — The repeatable way a team turns goals into delivered work. It covers workflow, communication, knowledge, and planning and tracking.

**Retrospective** — A short review after a project or milestone. It asks what went well, what did not, what was learned, and what to keep or change.

## S–Z

**Scope** — What the project will and will not do. Clear scope includes explicit exclusions.

**Stakeholder** — A person or group affected by the result or able to block it. Stakeholders need the right level of updates and a clear decision role.

**Status update** — A short, regular report of progress, blockers, decisions needed, and risks. See [Status update](templates/status-update.md).

**TaskNotes** — The Obsidian plugin used in the personal vault for individual task tracking, contexts, and time blocking.

**Throughput** — How many items finish in a period, usually per week. Useful for trends, not for comparison across teams.

**Two-vault model** — The split between a shared team vault for visibility and a personal vault for execution. Work moves between them by manual promotion.

**WIP** — Work in progress. The number of tasks started but not done.

**WIP limit** — A cap on how many tasks are in progress at once. It exposes bottlenecks instead of hiding them.
